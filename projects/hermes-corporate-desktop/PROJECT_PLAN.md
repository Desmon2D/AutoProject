# План разработки корпоративного desktop-агента

## Цель MVP

Windows-приложение на базе Hermes Desktop, которое:

- запускает Hermes Agent локально без web dashboard и обязательного Docker;
- использует OpenRouter и настраиваемую недорогую модель DeepSeek;
- подключается к корпоративным аналогам Jira, Confluence и Git через MCP;
- по умолчанию работает с корпоративными источниками только на чтение;
- хранит токены локально в защищённом хранилище ОС;
- устанавливается через обычный `.exe` или `.msi`.

## Текущее состояние

- Проект ведётся как downstream-ветка `NousResearch/hermes-agent`.
- Desktop-клиент находится в `apps/desktop` и использует Electron + React.
- Локальный backend запускается командой `hermes serve`.
- Desktop переименован в DIT Agent, использует отдельную красную тему и
  изолированный development-профиль.
- Open WebUI работает отдельно через `infra/local-ai/compose.ai.yaml`.
- Реализованы read-only MCP для GitLab, Staff, CFC, Jira и Confluence;
  Outlook/EWS подключается как внешняя опциональная зависимость.
- Общий реестр MCP для OpenWebUI находится в
  `infra/local-ai/mcp-servers.json`.
- Web-контейнер Hermes не используется как основа будущего приложения.
- Имеющиеся примеры MCP-конфигураций Jira и Confluence требуют отдельного аудита перед переносом секретов.

## Этап 1. Зафиксировать рабочую базовую сборку

- Создать отдельную ветку разработки от текущей ревизии Hermes.
- Установить зависимости репозитория.
- Запустить оригинальный `apps/desktop` в development-режиме.
- Проверить запуск локального `hermes serve`, создание сессии и стриминг ответа.
- Собрать неизменённый Windows installer.
- Зафиксировать команды сборки и версии Node, Python и npm.

Критерий готовности: оригинальное приложение стабильно запускается и собирается на текущем компьютере.

## Этап 2. Отделить продукт от upstream Hermes

- Выбрать название продукта, `appId`, иконку и цветовую схему.
- Заменить Hermes/Nous-брендинг в интерфейсе и установщике.
- Сохранить обязательное уведомление об MIT-лицензии Hermes.
- Выделить собственные настройки и компоненты так, чтобы обновления upstream переносились без массовых конфликтов.
- Отключить ненужные облачные и Nous-зависимые сценарии входа.
- Добавить русскую локализацию основных экранов.

Критерий готовности: приложение визуально и технически является отдельным продуктом, но продолжает использовать Hermes Agent как backend.

## Этап 3. Интегрировать OpenRouter

- Добавить onboarding для ввода OpenRouter API token.
- Хранить токен через Electron `safeStorage`/Windows DPAPI, не в исходниках и не в installer.
- Сделать model ID параметром конфигурации.
- Выбрать актуальную недорогую DeepSeek-модель после проверки цены, tool calling и размера контекста.
- Добавить проверку соединения и понятные ошибки: неверный токен, недостаточный баланс, rate limit, недоступная модель.
- Добавить лимиты стоимости: максимальное число итераций агента, контекст, предупреждение о расходах и опциональный дневной лимит.
- Настроить отдельные дешёвые модели для вспомогательных операций, если это действительно снижает стоимость.

Критерий готовности: новый пользователь вводит токен, выбирает DeepSeek и получает первый ответ без ручного редактирования конфигов.

## Этап 4. Спроектировать MCP-слой

### Общие требования

- Начать с read-only инструментов.
- Разделить Jira, Confluence и Git на независимые адаптеры с отдельными credentials и allowlist.
- Использовать общий слой для конфигурации, логирования, пагинации, таймаутов и обработки ошибок.
- Не отдавать модели сырые неограниченные ответы: нормализовать поля и ограничивать размер результата.
- Поддержать корпоративный proxy, собственные CA-сертификаты и нестандартные API endpoints.
- Добавить health check и диагностический вывод для каждого источника.
- Версии MCP-зависимостей закрепить, запуск непроверенных latest-пакетов запретить.

### Jira MCP

Минимальные инструменты:

- поиск задач по поддерживаемому корпоративным API запросу;
- получение задачи по идентификатору;
- комментарии, связи, статусы и история изменений;
- получение проектов и доступных полей.

Изменение задач, комментариев и статусов оставить выключенным до отдельного согласования прав и audit log.

### Confluence MCP

Минимальные инструменты:

- поиск страниц;
- получение страницы и метаданных;
- получение дочерних страниц;
- поиск по пространству;
- безопасное преобразование HTML/storage-разметки в компактный текст.

Создание и изменение страниц оставить выключенным на первом этапе.

### Git MCP

Минимальные инструменты:

- список доступных репозиториев;
- дерево файлов с ограничением по глубине;
- чтение файла по repository/ref/path;
- поиск по коду;
- история коммитов и diff;
- получение веток, tags, merge/pull requests, если корпоративный API это поддерживает.

Clone, push, merge и запись файлов запретить в MVP.

Критерий готовности: каждый источник независимо подключается, тестируется и предоставляет стабильный набор read-only tools.

## Этап 5. Исследовать корпоративные API

- Исследовать имеющиеся примеры MCP без копирования действующих токенов в проект.
- Отозвать и заменить токены, которые ранее хранились в открытом виде.
- Для каждого источника зафиксировать:
  - base URL и способ аутентификации;
  - доступные endpoints;
  - формат запросов и ответов;
  - пагинацию и лимиты;
  - модель прав;
  - отличия от оригинальных Jira, Confluence и Git API;
  - тестовый контур и тестовые данные.
- Подготовить контрактные fixtures с обезличенными ответами API.

Критерий готовности: есть документированный контракт каждого API и воспроизводимые тестовые примеры без корпоративных секретов.

## Этап 6. Встроить MCP в desktop-приложение

- Добавить экран «Корпоративные источники» вместо ручного редактирования `mcp.json`.
- Для каждого источника предоставить форму endpoint/auth, кнопку проверки и статус соединения.
- Добавить включение отдельных MCP tools и отображение их разрешений.
- Предустановить безопасные read-only конфигурации.
- Показывать пользователю, какой источник и какой tool вызывается агентом.
- Для будущих write-tools добавить обязательное подтверждение каждой операции.
- Корректно завершать дочерние MCP-процессы при закрытии приложения.

Критерий готовности: пользователь подключает три источника из UI и может искать и читать данные через чат.

## Этап 7. Безопасность

- Провести отдельное согласование допустимости передачи корпоративных данных в OpenRouter/DeepSeek.
- Добавить предупреждение и фильтрацию секретов перед отправкой контекста модели.
- Ограничить доступ агента к файловой системе рабочими каталогами/allowlist.
- Оставить выполнение terminal-команд выключенным или требующим подтверждения.
- Защититься от prompt injection в Jira/Confluence/Git-контенте: считать документы недоверенными данными, не инструкциями.
- Не логировать токены, пароли, Authorization headers и полные чувствительные документы.
- Проверить зависимости и installer на supply-chain риски.
- Добавить журнал вызовов MCP tools без секретных payload.

Критерий готовности: формально определены границы доступа, правила отправки данных во внешнюю модель и audit trail.

## Этап 8. Тестирование

- Unit-тесты нормализации и пагинации каждого API.
- Контрактные тесты по обезличенным fixtures.
- Интеграционные тесты MCP server ↔ Hermes.
- E2E: установка приложения → настройка OpenRouter → подключение источника → запрос из чата.
- Проверки offline/error-сценариев, timeout, rate limit и истёкших credentials.
- Проверка больших задач, страниц, файлов и репозиториев на переполнение контекста.
- Проверка Windows 10/11 и корпоративного proxy/CA.

Критерий готовности: основные пользовательские сценарии проходят автоматически, ошибки не приводят к зависшим backend/MCP-процессам.

## Этап 9. Сборка и распространение

- Настроить NSIS и MSI сборки.
- Получить сертификат подписи Windows или принять риск предупреждений SmartScreen для пилота.
- Добавить контролируемый канал обновлений.
- Подготовить конфигурацию по умолчанию без секретов.
- Добавить диагностику, экспорт безопасных логов и инструкцию для поддержки.
- Определить механизм регулярного переноса исправлений безопасности из upstream Hermes.

Критерий готовности: подписанный installer устанавливает, обновляет и удаляет приложение без ручной настройки runtime.

## Основные риски

| Риск | Мера |
| --- | --- |
| Корпоративные данные уходят внешнему LLM-провайдеру | До пилота получить явное согласование; при запрете использовать корпоративный или локальный inference endpoint |
| Корпоративные API отличаются от Jira/Confluence/Git | Не переиспользовать готовые серверы вслепую; реализовать адаптеры по фактическим контрактам |
| Токены попадут в Git, логи или installer | `safeStorage`, `.gitignore`, redaction логов, secret scanning |
| Prompt injection в документах и задачах | Недоверенный контент, ограниченный toolset, подтверждение действий, запрет write-tools по умолчанию |
| Агент выполнит опасную локальную команду | Sandbox/allowlist и интерактивное подтверждение terminal/file операций |
| Большие ответы MCP увеличат стоимость и контекст | Пагинация, фильтры, лимиты полей, summaries и точечное чтение |
| Обновления Hermes конфликтуют с форком | Минимизировать изменения core, держать кастомизацию в desktop UI и отдельных MCP-модулях |
| MCP-процессы зависнут после закрытия приложения | Управление process tree, timeout, graceful shutdown и тесты orphan-процессов |
| Windows SmartScreen блокирует installer | Подпись кода и стабильный publisher identity |
| Корпоративный proxy/TLS ломает соединения | Настраиваемый proxy и доверенное CA-хранилище, диагностика TLS без отключения проверки сертификатов |

## Порядок ближайших работ

1. Корпоративный экран настройки MCP вместо ручного редактирования конфигов.
2. Единый пользовательский процесс авторизации и удаления credentials.
3. Фильтрация чувствительных данных и защита от prompt injection.
4. Контрактные fixtures без корпоративных данных и интеграционные проверки.
5. Проверка сборки и установки на чистой Windows 10/11.
6. Security review, подпись installer и согласование канала распространения.
