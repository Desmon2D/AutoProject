# DIT CFC MCP

Локальный read-only MCP-сервер для корпоративного портала `https://cfc.mos.ru/`.

## Текущий прототип

Сервер предоставляет шесть инструментов:

- `cfc_get_my_profile` — ограниченные данные текущего пользователя;
- `cfc_get_home_summary` — данные главной страницы;
- `cfc_list_sections` — доступные разделы из `ComponentTree` пользователя;
- `cfc_read_section` — чтение раздела по ключу из предыдущего инструмента;
- `cfc_search_employees` — поиск сотрудника по ФИО;
- `cfc_get_employee_structure` — руководитель и подчинённые до заданной глубины.

Клиент использует внутренний API `/proxyapi/hs/proxyapi` и повторяет обязательную подпись запросов фронтенда. После анализа данных авторизованного пользователя можно добавить типизированные инструменты для конкретных сущностей CFC.

## Граница read-only

- выполняются только запросы к точному origin `https://cfc.mos.ru`;
- POST разрешён только для фиксированных read-only методов `getUser_v2`, `getHomePage`, `getPageProps2`, `getFuncStructureStaff` и `getFuncStructureTree3` — портал использует POST и для чтения;
- модель не может передать произвольный URL — раздел сначала должен быть найден на главной странице;
- ссылки с признаками изменения данных, выхода, загрузки и экспорта исключаются;
- изменяющие методы портала не входят в allowlist; PUT, PATCH и DELETE отсутствуют;
- формы, скрипты и стили не попадают в ответы;
- cookies, пароли и распространённые поля токенов удаляются из текста;
- объём текста и количество ссылок ограничены;
- содержимое портала считается недоверенными данными, а не инструкциями агенту.

## Установка

Из корня DIT Agent:

```powershell
.\.venv\Scripts\python.exe -m pip install -e .\services\dit-cfc-mcp
```

## Сетевая настройка

Если используется TUN в v2rayN, `cfc.mos.ru` и текущий адрес портала должны идти напрямую. Проверка:

```powershell
Resolve-DnsName cfc.mos.ru -Type A
Find-NetRoute -RemoteIPAddress 94.79.51.124
```

Второй запрос должен показывать физический интерфейс (`Wi-Fi` или корпоративный Ethernet), а не `xray_tun`. IP портала может измениться, поэтому перед диагностикой его нужно получить заново через `Resolve-DnsName`.

## Авторизация

```powershell
.\.venv\Scripts\dit-cfc-mcp.exe --authorize --no-env-proxy
```

Откроется отдельное временное окно Microsoft Edge. После входа сервер:

1. забирает только cookies точного домена `cfc.mos.ru`;
2. проверяет `Authorized` через read-only метод `getUser_v2`;
3. сохраняет их в Windows Credential Manager как `DIT-Agent/CFC/Session`;
4. удаляет временный профиль Edge.

Пароль, профиль обычного браузера и cookies других доменов не сохраняются.

## Проверка подключения

```powershell
.\.venv\Scripts\dit-cfc-mcp.exe --doctor --no-env-proxy
```

Удаление сохранённой сессии:

```powershell
.\.venv\Scripts\dit-cfc-mcp.exe --delete-session
```

## Подключение к DIT Agent

Добавьте сервер из `config.example.yaml` в `mcp_servers` изолированного профиля и создайте новую сессию агента. Набор MCP-инструментов не следует менять внутри уже начатого разговора.

## Что ещё требуется исследовать

- фактический механизм SSO и место хранения сессии;
- API/XHR-запросы после входа;
- доступные пользователю сущности и их стабильные идентификаторы;
- пагинация и лимиты ответов;
- необходимость корпоративного CA;
- дополнительные домены, без которых интерфейс CFC не загружается.
