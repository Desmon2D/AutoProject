# План сценариев

Источник требований: [полное описание архитектуры](../architecture.md), разделы 2–7 и 16.

## Контракт сценария

Сценарий описывается в JSON и содержит:

- тип исходного события;
- начальный шаг;
- набор шагов;
- тип и параметры каждого шага;
- необходимые расширения;
- правила технических повторных попыток;
- переходы по `SUCCESS` и `FAILURE`.

Поддерживаются ровно три базовых типа шага:

- `command` — выполнение заранее определённой команды;
- `agent` — запуск агента в Docker-песочнице;
- `review` — ожидание решения пользователя.

Сценарий является ориентированным графом и может содержать циклы. Технический `ERROR` обрабатывается повторной попыткой и не является переходом по ветке `FAILURE`.

## Сценарий `implement-ticket`

1. Событие `plane.issue.ready_for_development` запускает агента разработки.
2. Репозиторий определяется по сопоставлению проекта Plane с репозиторием Gitea.
3. Агент изменяет рабочий код, запускает существующие проверки и отправляет стабильную ветку
   `automation/<workflow_id>`.
4. Оркестратор проверяет, что удалённая ветка указывает на заявленный полный хеш коммита.
5. Ветка и коммит сохраняются в структурированных ссылках задачи Plane. Запрос на слияние на этом
   этапе не создаётся.
6. Неуспешный результат записывается в Plane и завершает процесс с `COMPLETED / FAILURE`.

## Сценарий `test-ticket`

1. Событие `plane.issue.testing` получает репозиторий из проекта Plane, а рабочую ветку и коммит —
   из завершённого `implement-ticket` или структурированных ссылок задачи.
2. Первый агент пишет только тесты и отправляет отдельную стабильную ветку, не выполняя тесты.
3. Второй агент проверяет точный коммит, соответствие тестов требованиям и запускает полный набор
   проверок без изменения файлов.
4. Ошибочные тесты один раз возвращаются первому агенту. Ошибка продукта возвращает задачу в
   разработку без создания запроса на слияние.
5. После успешной проверки оркестратор создаёт один итоговый запрос на слияние с рабочим кодом и
   тестами и ожидает принятия либо закрытия пользователем.
6. Решение пользователя синхронизируется с состоянием и комментариями Plane.

## Сценарий `gitea-push`

Обычные отправки в Gitea создают процесс краткого разбора события. Отправки в служебные ветки
`automation/*` игнорируются, поскольку уже принадлежат родительскому процессу разработки или
тестирования.
