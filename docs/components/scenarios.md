# План сценариев

Источник требований: [полное описание архитектуры](../architecture.md), разделы 2–7 и 16.

## Контракт сценария

Сценарий описывается в JSON и содержит:

- этап (`analysis`, `development`, `testing`, `bug-finding`, `operations` или `system`),
  отображаемое название и краткое описание;
- тип исходного события;
- начальный шаг;
- набор шагов;
- тип и параметры каждого шага;
- необходимые расширения;
- правила технических повторных попыток;
- переходы по `SUCCESS` и `FAILURE`.

Поддерживаются ровно три базовых типа шага:

- `command` — выполнение заранее определённой команды;
- `agent` — запуск агента в Docker-песочнице;
- `review` — ожидание решения пользователя.

Сценарий является ориентированным графом и может содержать циклы. Технический `ERROR` обрабатывается повторной попыткой и не является переходом по ветке `FAILURE`.

Каждый workflow закрепляет неизменяемый снимок графа и его SHA-256. Новая версия JSON применяется
только к новым событиям и не изменяет переходы уже запущенных или ожидающих процессов.

Текущий каталог разделён по этапам: `analysis-document` относится к аналитике,
`implement-ticket` — к разработке, `test-ticket` — к тестированию, `bug-finding` — к поиску
ошибок. Служебные сценарии отнесены к `operations` и `system`.

## Сценарий `analysis-document`

1. Пользователь передаёт аналитический запрос и необязательное название документа через панель
   или `POST /v1/analysis`.
2. Оркестратор выполняет полный и короткие тематические запросы к BookStack через SWIRL,
   объединяет выдачу взвешенным Reciprocal Rank Fusion и загружает полный текст лучших кандидатов
   в доверенный слой. Главная тема берётся из первой содержательной положительной части запроса;
   отрицательные директивы не превращаются в поисковые термины.
3. Markdown делится по разделам и абзацам, блоки ранжируются относительно запроса и упаковываются
   с общим лимитом контекста и разнообразием источников. Агент может получить полный документ через
   `swirl_fetch_document`, отделяет факты от выводов и фиксирует пробелы.
4. Нерелевантные блоки отбрасываются по минимальному порогу, а в контекст добавляется сводка
   покрытия терминов, чтобы агент видел пробелы и риск ухода от темы.
5. Успешный результат обязан содержать UTF-8 Markdown-файл с заголовком и ссылками на источники.
6. Оркестратор проверяет метаданные, безопасный путь, наличие, содержимое, хотя бы одну Markdown-
   ссылку и цитирование источника, покрывающего главную тему, после чего
   публикует его как скачиваемый артефакт workflow.

## Сценарий `implement-ticket`

1. Перевод задачи в `Ready for development` запускает workflow и автоматически меняет состояние
   Plane на `In development`.
2. Репозиторий берётся из корневой Gitea-ссылки в разделе Links задачи Plane. Оркестратор принимает
   только ссылку на настроенный Gitea и репозиторий из `GITEA_ALLOWED_REPOSITORIES`. Если ссылки нет,
   используется сопоставление проекта Plane из `PLANE_PROJECT_REPOSITORIES`; маркер в описании
   поддерживается только для обратной совместимости.
3. Для поиска документации через SWIRL используется название вместе с описанием задачи. Полные
   тексты лучших документов проходят ранжирование и попадают в ограниченный контекст агента;
   текущий код и правила репозитория остаются источником истины для реализации.
4. Агент формирует перечень требований, проверяет относящиеся к ним код, тесты, конфигурацию и
   документацию, затем делает минимальное целостное изменение. Существенная неоднозначность
   возвращается как бизнес-блокировка, а ошибки Git, сети и API — как технические ошибки.
5. Агент запускает предусмотренные проектом проверки, проверяет итоговый diff и отправляет
   стабильную ветку
   `automation/<workflow_id>`.
6. Оркестратор проверяет, что удалённая ветка указывает на заявленный полный хеш коммита.
7. Репозиторий, ветка и коммит сохраняются в структурированных ссылках задачи Plane. Задача
   переводится в `Development review`, а workflow — в `WAITING`. Запрос на слияние на этом этапе
   не создаётся.
8. Одобрение человеком переводит задачу в `Testing`, завершает `implement-ticket` и запускает
   `test-ticket`. Возврат на доработку переводит задачу в `In development` и запускает следующую
   итерацию того же workflow с обновлённым описанием и комментариями review.
9. Перевод активной задачи в `Cancelled` отменяет связанный workflow. Неуспешная бизнес-реализация
   записывается в Plane и переводится в `Development review` для ручного уточнения.

## Сценарий `test-ticket`

1. Событие `plane.issue.testing` получает репозиторий из проверенной ссылки задачи или резервного
   сопоставления проекта Plane, а рабочую ветку и коммит — из завершённого `implement-ticket` или
   структурированных ссылок задачи.
2. Агент пишет только недостающие тесты и отправляет отдельную стабильную ветку. Если все требуемые
   проверки уже существуют, ветка создаётся без нового коммита и это считается успешным результатом.
3. Оркестратор проверяет, что тестовая ветка является потомком точного коммита реализации, после
   чего запускает заявленную команду в отдельном контейнере без модели, сети и секретов. Для
   Pytest, Jest, Go и .NET формируется структурированный отчёт; также распознаются unittest и TAP.
   Успешный exit code без хотя бы одного реально выполненного теста считается ошибкой тестового
   кода. Exit code, счётчики и вывод берутся только из этого запуска.
4. Ошибочные тесты один раз возвращаются агенту. Ошибка продукта возвращает задачу в разработку
   вместе с тестовой веткой, точным коммитом и отчётом, без создания запроса на слияние.
5. После успешной проверки оркестратор создаёт один итоговый запрос на слияние с рабочим кодом и
   тестами и ожидает принятия либо закрытия пользователем.
6. Решение пользователя синхронизируется с состоянием и комментариями Plane.

Обычные push-события Gitea не создают отдельный workflow и не вызывают модель. Вебхук Gitea
используется только для продолжения сценариев после событий pull request и review.

## Сценарий `bug-finding`

1. `POST /v1/bug-finding` принимает разрешённый Gitea-репозиторий, Git ref, область поиска,
   необязательные симптомы, логи и ограничения.
2. Агент клонирует только указанный репозиторий, закрепляет точный commit и не изменяет и не
   отправляет product-код.
3. Результат содержит `data.bug_report`, Markdown-отчёт и для каждого дефекта evidence,
   severity, confidence, root cause, воспроизведение и минимальный reproducer-тест.
4. Оркестратор накладывает reproducer на чистый архив точного commit и запускает его без модели,
   сети и секретов. Дефект подтверждается только вердиктом `PRODUCT_FAILURE`.
5. Невоспроизводимый отчёт один раз возвращается исследователю вместе с авторитетным выводом
   проверки. После повторной ошибки workflow завершается бизнес-неуспехом.
6. Отсутствие найденных дефектов является успешным завершением исследования со статусом
   `NO_FINDINGS`, а не технической ошибкой.
